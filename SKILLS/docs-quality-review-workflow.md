# Docs Quality Review Workflow

## When to use

Use this workflow when creating or editing repository documentation, onboarding guides, release notes, or technical how-to content.

## Required inputs

- Audience (contributors, operators, end users).
- Scope of doc change and linked code/features.
- Source of truth references (files, commands, configs).
- Expected output format (README section, playbook, runbook, etc.).
- Quality bar (accuracy, completeness, brevity, examples).

## Step-by-step procedure

1. Identify the canonical source files and commands before drafting text.
2. Draft docs using task-oriented sections and concise headings.
3. Include prerequisites, environment setup, and exact command examples.
4. Cross-check claims against current code/config; remove stale statements.
5. Add links to adjacent docs to improve discoverability.
6. Ensure terminology is consistent across README and operational docs.
7. Proofread for ambiguity, duplication, and contradictory instructions.
8. Validate markdown rendering and anchor/link correctness.

## Validation checklist

- [ ] Every procedural claim maps to current code/config.
- [ ] Commands are copy-pasteable and scoped to correct working directory.
- [ ] Links resolve locally (relative paths) or externally.
- [ ] New docs are discoverable from root-level entry points.
- [ ] No contradictory setup instructions remain.
- [ ] Formatting renders cleanly in Markdown viewers.

## Common pitfalls specific to this repo

- Root README includes mixed historical and autogenerated content; place new guidance clearly to avoid confusion.
- Setup steps can diverge (`npm`, `yarn`, `pnpm`) if examples are not kept aligned.
- Environment variable naming in docs can drift from `.env.example`.
- v0/Vercel deployment metadata can distract from contributor-facing instructions unless sectioned clearly.
